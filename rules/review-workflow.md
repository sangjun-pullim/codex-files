# Review workflow

Read before conducting or acting on reviewer assessments of code, plans, or instructions.
This is the canonical procedure referenced by AGENTS.md and the implementation skills.
Required independent-review boundaries remain in AGENTS.md.

- **리뷰 루프** — Apply this loop to reviewer assessments of code, plans, and instructions, inside or outside skills. Fix the requested scope and baseline change; subsequent rounds review corrections and affected areas. In each round, classify only CRITICAL/HIGH findings as `ACCEPTED` (to fix) or `REJECTED` with evidence. Reject out-of-scope findings. Do not fix MEDIUM/LOW findings in this loop; report them with rationale at completion. Separately requested/approved improvements and mandatory verification still proceed.
- **동작 지적의 재현** — A code finding that asserts an input/state produces a wrong outcome is a bug fix. Apply **리뷰 정지** first; for a finding outside the stopped scope, run a reproduction test before correcting code. Reuse an existing test that exercises the claimed defect, or write/extend one when coverage is missing. If it passes, verify that it exercises the claimed conditions and required path; repair missing coverage. If a suitable reproduction still passes and no other evidence supports the defect, reject that finding. For defects hard to reproduce (e.g. races or environment-dependent failures), judge from concrete code paths and evidence of the wrong outcome, and report remaining verification. Remove tests added solely for a rejected finding; retain pre-existing tests and tests of separate requirements.
- **리뷰 정지** — After disposition and before any correction, including reproduction tests, stop work on an ACCEPTED finding if it: (a) appears in round 3 or later; (b) recurs after being fixed in this loop; or (c) concerns the same rule/decision changed by this work as a blocking finding ACCEPTED in the immediately preceding round. Include missed or contradictory copies of the same rule; exclude independent findings that merely share review criteria.
  - Freeze that finding's affected code/rules, dependent work, and reproduction tests until the user resumes it. Do not retry the stopped fix under another label.
  - Continue other authorized corrections and verification only when their correctness does not depend on the stopped decision and they do not alter the frozen code/rules. Record that independence. If the work is intertwined or independence cannot be established, stop the intertwined work as a whole.
  - Preserve the loop's round count while independent work continues; a scoped stop is not a new loop. Independent corrections still require the usual verification and review.
  - Report the stopped scope, cause, and a new design direction (declare ownership boundaries, unify under an existing concept, or use one canonical source with links). Record stopped and blocked findings as `UNRESOLVED` in `## Review Notes` when spec editing is allowed; otherwise record them in the report. Independent progress does not resolve those findings or permit whole-task completion.
- **리뷰 종료·재개** — End a loop as complete only after reproduction disposition leaves no ACCEPTED findings or stopped scope and independent review confirms resolution of all retained UNRESOLVED findings. Keep fixed ACCEPTED entries in their original round for verification in the next review. Report REJECTED findings with reasons, also in `## Review Notes` when the spec is editable. For read-only requests, finish with dispositions and proposed fixes; do not mark open findings resolved. After a stop, the user's “계속” authorizes resuming the stopped corrections within the approved scope using the chosen direction, or the recommended direction if none was chosen, and a new loop from round 1. Exclude earlier rounds/fixes from the new loop's stop count; retain UNRESOLVED entries until independent review confirms resolution. Ask the user to choose first if changing an external contract or declaring another team's ownership is necessary.
